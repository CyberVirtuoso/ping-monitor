# ping-monitor

Оперативный мониторинг доступности узлов во время сетевых работ. Каждый адрес проверяется независимым воркером. Отображение и журналирование отделены от опроса. Все примеры и автоматические тесты используют только документационные адреса TEST-NET / 2001:db8::/32 или локальный файл целей.

## Требования и установка

Linux, Bash ≥ 4.4, iputils-ping, GNU coreutils (в том числе timeout, stty, sleep, mktemp, mv, rm, cat, date); util-linux/flock для журнала. Для интерактивного интерфейса — UTF-8 и ANSI-совместимый терминал. Root не нужен, если разрешены ICMP-проверки. Python 3 нужен только для регрессионных тестов.

```bash
bash -n ping-monitor.sh
sudo install -m 0755 ping-monitor.sh /usr/local/bin/ping-monitor
ping-monitor --help
```

## Запуск

```bash
ping-monitor -f hosts.txt -i 0.5 -W 0.5 --standard \
  -l "network-$(date +%F_%H-%M-%S).tsv" --samples
```

`hosts.txt` — один или несколько числовых IPv4/IPv6 на строке, комментарии `#`, пустые строки и CRLF разрешены. Дубликаты исключаются. Адреса допускается передавать аргументами. `--auto` по умолчанию выбирает самый подробный профиль, помещающийся в ширину терминала; явный профиль также сокращается, если не помещается. Если высоты недостаточно, таблица разбивается на автоматически сменяющиеся каждые 5 секунд страницы. Суммарные счётчики относятся ко всем целям. Для крайне маленького окна увеличьте размер терминала. `--plain` отключает перерисовку и ограничение ширины/высоты, итоговый отчёт всегда полный.

| Профиль | Содержимое |
|---|---|
| `--compact` | IP, статус, потери |
| `--standard` | Основные показатели: потери, процент потерь, ошибки, сбои, RTT, возраст результата |
| `--extended` | Дополнительно число отправок, доступность, длительности сбоев |
| `--full` | Все 19 столбцов, включая RTT min/avg/max/MDEV, фактический период и ошибки парсинга RTT |

Проверка Jumbo Frames IPv4 при MTU 9000:

```bash
ping-monitor -I bond5 -s 8972 -M do -i 0.5 -W 0.5 -f hosts.txt
```

Для IPv6 без дополнительных заголовков полезная нагрузка для MTU 9000 — 8952 байта. Поддержка режима PMTU зависит от версии iputils и прав.

## Семантика показателей

- UP: получен ICMP-ответ; DOWN: одна учтённая отправка, ответа нет; ERROR: локальная ошибка/неопределённый результат (не считается потерей); STALE: нет актуального результата/авария воркера; WAIT: ожидание первой проверки.
- Один вызов `ping -n -c 1 -W ...` без `-w`. Внешний GNU `timeout --foreground -k 0.2` задаёт дополнительный абсолютный предел `ceil(W)+1` секунд, после чего результат watchdog считается ERROR. Неизвестное число отправок не записывается как потеря.
- Процент доступности — доля успешных учтённых отправок, не временной SLA. ERROR и незавершённые пробы исключаются. Оценка длительности DOWN начинается с отправки первой неуспешной пробы и заканчивается успешной пробой либо ERROR; это не точная физическая длительность отказа. При STALE открытый сбой ограничивается последним подтверждённым результатом.
- RTT MDEV — приближённое популяционное стандартное отклонение числовых RTT. Значения `time<...` не включаются в агрегаты. Неизвлечённый RTT успешной пробы отдельно учитывается в `rtt_parse_errors` и не меняет UP.
- Экран рисуется абсолютным позиционированием, очищением строки и остатка кадра. Длинная диагностика на экране обрезается. Полные сохранённые диагностические сообщения (до 500 байт исходного вывода) доступны в TSV/обычном выводе во время ошибки. В интерактивном режиме показывается одна текущая ошибка; остальные можно изучить в журнале. При восстановлении строки ошибок исчезают.

## Журнал и завершение

TSV: 28 полей, новый `rtt_parse_errors` в конце. Используйте новый файл при переходе с v3.1. STATE (смена состояния) и SAMPLE (результат пробы) — разные записи одной проверки; `--samples` создаёт запись для каждой завершённой пробы. Без `--samples` повторная ошибка парсинга RTT при неизменном UP также записывается как RTT_PARSE. Сортировка событий разных узлов может отличаться от времени проб. Очередь ограничена `--queue` (128 записей/узел); отброшенные и невыгруженные записи учитываются отдельно. `TMPDIR=/dev/shm` позволяет размещать очередь и снимки в tmpfs при достаточной памяти.

Ctrl+C/SIGTERM/SIGHUP запускают ограниченное ожидание дочерних заданий; отдельные группы процессов получают TERM/CONT, а оставшиеся — KILL. При непрерываемой блокировке ядра остановка процесса не гарантирована; если завершение группы не подтверждено, скрипт сообщает об этом и сохраняет временный каталог. Операции с зависшей файловой системой также могут задержать остановку. SIGKILL самого монитора не позволяет выполнить trap. При нормальной остановке выводится полный итоговый отчёт, восстанавливается исходный экран и курсор.

## Масштабирование

Ориентиры для начала: 1–10 узлов — 0.1–0.2 с; 10–30 — 0.2–0.5 с; 30–50 — 0.5 с; 50–100 — 0.5–1 с; более 100 — от 1 с, после нагрузочного тестирования. Это рекомендации, не подтверждённые предельные характеристики. При расчётной интенсивности от 200 проб/с или 100 узлов монитор предупреждает о нагрузке. Каждый опрос создаёт процессы ping и timeout, а также выполняет файловые операции. Следите за ПЕРИОД, ДАВН., STALE и потерями записей. Для более крупных систем рассмотрите специализированный монитор с постоянными ICMP-сокетами.

## Регрессионные тесты

Из корня распакованного архива:

```bash
python3 ping-monitor-tests/test_ping_monitor.py
```

Тесты подменяют `ping` локальным процессом, не отправляют ICMP и проверяют состояние, журнал, независимость узлов, сигналы и последовательности ANSI в Linux PTY. Реальный сетевой тест необходимо выполнять в своей среде: до работ убедиться в успешном ICMP, затем проверить контролируемый разрыв и восстановление. Сравните потери с независимым `ping -n -c 1 -W 1` без `-w`. Проверка Bash 4.4 и конкретного терминального эмулятора также рекомендуется.
